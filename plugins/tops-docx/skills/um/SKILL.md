# 用户操作手册 (um)

## 用途

撰写面向最终用户的**用户操作手册**，说明功能用途、界面位置与操作步骤，输出为 UTF-8 编码的 markdown 文件。

本技能只负责「写成 markdown」。需要 Word 文档时，由使用者再调用 `md2docx` 技能按 docx 模板转换。

## 触发条件

- 使用者要求「写用户手册」「写操作手册」「写使用说明」时使用。
- 使用者提供 PRD 并要求面向用户产出操作说明时使用。
- 使用者说 `/um` 时使用。

## 输入来源与证据优先级

手册中「叫什么、在哪点」由界面依据决定，「写哪些功能」由 PRD 决定。按以下优先级取证，高优先级来源覆盖低优先级来源：

| 优先级 | 来源 | 用于确认 |
|--------|------|----------|
| 1 | 实现代码：前端页面/路由/菜单定义、按钮与表头文案、提示信息与错误码 | 菜单层级、按钮文案、字段名称、提示语 |
| 2 | 界面原型：原型稿（HTML 原型、Axure、设计稿）、演示截图 | 页面结构、弹窗字段、列名 |
| 3 | 测试用例、验收记录、用户问题记录 | 实际菜单路径、提示语原文、状态流转、异常场景 |
| 4 | 接口说明、部署说明、使用说明、FAQ | 前置条件、外部系统依赖、时间/数量类约束 |
| 5 | PRD | 功能范围、业务规则、操作先后顺序 |

**检索与降级规则**：

- 检索时先查使用者指定目录下的原型、测试用例、部署与使用说明、FAQ 等界面依据类文档，再检索代码库。
- 按上表自上而下取证：高优先级来源缺失时，降级取下一级；取证结论存疑的，列入待确认清单。
- 文档可能因加密、损坏或格式不兼容而无法读取；读不到即降级取证，**不要根据文件名或常识臆测其内容**。
- 所有来源都查不到对应功能时，该功能不写入手册，列入待确认清单；确实要写时先向使用者确认。

## 工作流

1. 确认项目/特性名称、使用者指定的输出目录与文档基准版本。
2. 取得 PRD，整理出手册要覆盖的功能清单。
3. 生成「功能项 → 手册章节」映射表，与使用者确认覆盖范围后再成文。映射表中有功能项无章节、或有章节无功能项时，先解决再写。
4. 按证据优先级定位每个功能的界面与操作路径：菜单、页面、按钮、字段、提示语、状态值。
5. 按「章节骨架」逐章成文，操作步骤以用户视角描述：进哪里、点什么、填什么、看到什么。
6. 按「自检清单」逐项核对，再向使用者交付。

## 冲突处理

- 界面文案冲突：按证据优先级取高者，差异及采用的版本列入待确认清单。
- 业务规则冲突（同一约束在不同来源中的取值或结论不一致，如时间间隔、数量阈值、状态流转结果）：正文只写用户可感知的行为，**不写死有争议的具体数值**；数值类争议一律列入待确认清单。
- 手册正文中不出现「待确认」「TODO」「以实际为准」「建议联系开发」等字样；不确定内容要么按上述规则写实，要么不写。

## 章节骨架

手册按下述多级章节组织，`<...>` 处按实际项目替换，`——` 后为该节应包含的内容。固定章节不得删减；项目无对应内容时删除该节并顺延编号，不留空节。

```
1. 概述
   1.1 编写目的
   1.2 适用范围
       ——覆盖的功能与业务环节，以及明确不包含的部分
   1.3 术语与缩写
       ——表格：术语/缩写、全称或含义、说明
   1.4 业务流程总览
       ——按操作顺序编号列出完整业务链路

2. 运行环境与安装
   2.1 客户端环境
       ——表格：浏览器、分辨率、外设要求
   2.2 服务端与外部系统环境
       ——表格：依赖的外部系统及其开通/可用条件
   2.3 首次使用前的准备
       ——账号与权限开通、前置档案与基础数据准备

3. 软件功能说明
   3.1 菜单结构
       ——表格：菜单层级、功能项、用途，覆盖系统全部功能模块
   3.2 <功能模块一>
       3.2.1 页面与字段
           ——本模块各页面之间的进入关系与跳转顺序，每个页面一张表格：字段、说明
       3.2.2 状态说明
           ——本模块的关键状态，每张表格：状态值、含义、该状态下可执行的操作
       3.2.3 主要按钮
           ——表格：按钮、所在页面、作用
       3.2.4 计算与显示规则
           ——时间、时长、数量等由系统计算的字段规则，本模块无此类规则时删除本节
   3.3 <功能模块二>
       ——结构同 3.2
   3.N <功能模块 N>
       ——结构同 3.2

4. 应用场景操作流程
   4.1 场景总览
       ——场景清单及其先后顺序
   4.2 <应用场景一>
       4.2.1 适用场景
       4.2.2 前提条件
       4.2.3 操作步骤
       4.2.4 注意事项
   4.3 <应用场景二>
       ——结构同 4.2
   4.N 异常处理场景
       ——结构同 4.2，承载异常判定、取消与重新执行的完整闭环

5. 常见问题与故障处理
   5.1 <问题一>
       ——现象、原因、处理
   5.2 <问题二>
       ——结构同 5.1

6. 文档修订记录
   ——表格：版本、日期、修订内容、修订人，位于正文最后
```

结构约束：

- 全文编号连续，层级不超过四级；同一模块、同一场景在 3 章与 4 章中的命名必须一致，并与 3.1 菜单结构中的功能项对应。
- 1 章只写编写目的、适用范围、术语与业务流程总览，不写设计原理与技术架构。
- 2 章只写客户端环境、外部系统依赖、首次使用前的准备，不写部署架构、服务器配置与运维操作。
- 3 章先给全局菜单结构，再按功能模块逐个展开；模块划分以 3.1 的功能项为准，每个模块必须包含页面与字段、状态说明、主要按钮三节，计算与显示规则仅在该模块存在此类规则时保留；不写操作步骤。
- 4 章的场景按业务发生顺序排列，每个场景独占一章并包含适用场景、前提条件、操作步骤、注意事项四段，不得缺段或合并；不写设计原因、接口细节与技术实现。
- 5 章每个问题独占一节并包含现象、原因、处理三段，问题来源优先取 PRD 中的校验提示语与测试用例中的异常场景；不写需要研发介入的内部排查过程。
- 6 章文档修订记录固定放在正文最后，不并入概述；每次修订追加一行，不覆盖历史记录。

## 写作规范

**界面用语**

- 按钮、菜单、字段、提示语的名称用中文引号包裹，与界面文案逐字一致，不缩写、不翻译、不改写。
- 菜单路径按界面实际的分隔符书写，不自行替换成箭头或其他符号。
- 术语首次出现时给出全称与含义，后续沿用界面上的叫法。
- 同一规则（状态、权限、时间、字段可编辑性）在多处出现时，各章表述必须一致。

**操作步骤**

- 每步写成「操作 + 预期结果」的单句，例：点击「确认」，系统校验通过后提交，列表新增一行数据。
- 一步只做一件事，步骤按顺序可直接照做，不依赖未说明的前提。

**内容边界**

- 不写接口名称、请求参数、表名、字段名、状态码等技术细节；状态值仅在该状态直接展示在界面时才允许出现。
- 不得引用其他文档，不出现「见需求文档」「详见设计文档」一类跨文档引用；允许引用手册自身的章节号（如「详见 3.5 节」）。

**格式**

- 表格不嵌套，列表不嵌套。
- 不使用 mermaid 或流程图代码块，流程用编号列表或文字描述。
- 文件为 UTF-8 编码，无 BOM。

## 输出

### frontmatter

文件顶部必须包含以下字段（字段名固定，供 `md2docx` 识别封面信息）：

```yaml
---
title: <项目或特性名称> 用户操作手册
doc-type: UM
version: V1.0
author: <作者>
date: <YYYY-MM-DD>
confidentiality: 限制
cover: true
toc: true
---
```

取值规则：`author` 默认取 PRD 的修订人或使用者指定的人；`date` 取成文当天；首版 `version` 为 V1.0。确实无法确定时留空字符串，并列入待确认清单。

### 文件名

命名为 `<项目或特性名称>_用户操作手册_<YYYYMMDD>.md`，与同项目其他文档的命名风格保持一致。

### 图片

- 截图统一放在 md 文件同级的 `images/` 目录，命名 `um-<章节号>-<序号>.png`，引用写法 `![图题](images/xxx.png)`。
- 没有可用的截图素材时，不写入指向不存在文件的图片引用，也不留空占位。

## 交付说明（仅在对话中输出，不写入手册）

交付手册时在对话中说明两项：

- **待确认清单**：列出需要使用者确认的事项，每条写明问题与依据（例如「某时间间隔在不同来源中取值不一致」）。
- **建议截图清单**：按章节列出建议补充的页面截图及建议截取的内容；没有可用的截图素材时必须输出。

## 自检清单

**结构完整性**

- frontmatter 字段齐全且取值符合规则。
- 1~6 章齐全；3 章每个功能模块的页面与字段、状态说明、主要按钮三节齐全；4 章每个场景四段齐全；5 章每个问题三段齐全。

**内容准确性**

- 每个菜单、按钮、字段、提示语都能追溯到具体证据来源，无虚构操作路径。
- 操作步骤可照做：进哪里、点什么、填什么、看到什么均已写明。
- 状态、权限、时间、字段可编辑性等规则在各章表述一致。
- 无跨文档引用，无接口、表名、字段名等技术细节泄漏。

**格式规范**

- 表格与列表均为单层，无嵌套；不使用 mermaid 或流程图代码块。
- 全文无「待确认」「TODO」等字样残留。
- 文件为 UTF-8 编码且无 BOM。
