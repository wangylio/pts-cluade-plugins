# 概要设计文档 (hld)

## 用途

推导并撰写**高层设计文档 / 概要设计文档**，描述系统总体架构、模块划分、模块间交互、数据与接口的概要设计，输出为 UTF-8 编码的 markdown 文件。

本技能只负责「写成 markdown」。需要 Word 文档时，由使用者再调用 `md2docx` 技能按 docx 模板转换。

## 触发条件

- 使用者要求「写概要设计」「写高层设计」「写 HLD」时使用。
- 使用者提供 PRD 内容并要求据此产出设计文档时使用。
- 使用者说 `/hld` 时使用。

## 输入来源与证据优先级

设计内容**由 PRD 推导**，PRD 之外的信息只用于补全设计约束。按以下优先级取证，高优先级来源覆盖低优先级来源：

| 优先级 | 来源 | 用于确认 |
|--------|------|----------|
| 1 | 使用者当前在对话中提供的 PRD 内容或需求要点 | 功能范围、业务规则、非功能指标、验收要求 |
| 2 | 使用者指定路径的本地 PRD 文件 | 需求细节、需求编号、异常与边界 |
| 3 | 使用者提供的架构资料：现有系统设计、部署图、接口文档、运行环境说明 | 架构现状、外部系统边界、部署形态 |
| 4 | 使用者口述的补充说明 | 优先级 1~3 未覆盖的设计约束 |

**检索与降级规则**：

- 优先使用使用者当前提供的形式；对话中已粘贴的内容不再重复读取文件。
- **不要求 PRD 文件存在于固定路径**——本技能必须能脱离仓库中的 PRD 文件独立成文。
- 文件可能因加密、损坏或格式不兼容而无法读取；读不到即降级取证，**不要根据文件名或常识臆测其内容**。
- 优先级 1~3 都拿不到 PRD 内容时，先向使用者索取，不得凭空设计。
- 推导所需的关键信息缺失时（如部署形态、外部系统、性能约束），逐项向使用者提问确认；确实无法确认的，登记到第 8 章。

## 工作流

1. 确认项目/特性名称、使用者指定的输出目录与设计范围。
2. 取得 PRD 内容，提炼功能清单（F 编号）与非功能要求（NFR 编号）。
3. 按需求分组划分模块，形成 4.1 模块清单与需求编号的对应关系；出现需求无模块承载时，先与使用者确认再成文。
4. 按「章节骨架」逐章推导成文：模块划分对应 PRD 的功能分组，不要凭空增加功能；每个模块写清职责边界与对外交互；架构选择要给出理由。
5. 按「自检清单」逐项核对，再向使用者交付。
6. 告知使用者将要写入的文件路径；目标文件已存在时先询问覆盖还是改名，确认后再写入。

## 冲突处理

- 使用者当前答复与既有 PRD 文件不一致：以使用者当前答复为准，差异及采用的版本列入第 8 章。
- PRD 不同章节之间冲突：以带有需求编号的条款为准；仍无法判断时向使用者确认，确认前不在正文写死结论。
- 设计取舍存在多个可行方案：正文写明采用方案与理由，未选方案只做简要对比，不展开设计。
- 无法确认的设计决策不写死，登记到第 8 章，并写明对哪些模块或指标有影响。

## 章节骨架

文档按下述多级章节组织，`<...>` 处按实际项目替换，`——` 后为该节应包含的内容。固定章节不得删减；项目无对应内容时删除该节并顺延编号，不留空节。

```
1. 文档概述
   1.1 编写目的
   1.2 设计范围
       ——覆盖的系统、模块与业务环节，以及明确不包含的部分
   1.3 读者对象
       ——表格：读者角色、关注内容
   1.4 术语与缩略语
       ——表格：术语/缩略语、全称或含义、说明

2. 设计目标与约束
   2.1 设计目标
       ——可判定的目标，逐条编号，并标明对应的需求编号
   2.2 设计约束
       ——表格：约束项、来源、对设计的影响
   2.3 设计取舍
       ——关键取舍：候选方案、采用方案、理由

3. 总体架构
   3.1 系统组成
       ——表格：组成部分、职责、部署位置
   3.2 分层与分区
       ——层次或分区的划分依据与边界
   3.3 部署形态
       ——部署单元、网络区域、与外部系统的连接方式
   3.4 外部系统边界
       ——表格：外部系统、交互内容、交互方向
   3.5 架构选型理由
       ——选型依据、替代方案与不采用的原因

4. 模块划分与职责
   4.1 模块清单
       ——表格：模块编号、模块名称、职责、对应需求编号
   4.2 <模块一>
       4.2.1 职责与边界
           ——本模块负责什么、不负责什么
       4.2.2 对外交互
           ——表格：交互对象、交互内容、交互方式
   4.3 <模块二>
       ——结构同 4.2
   4.N <模块 N>
       ——结构同 4.2

5. 模块间交互
   5.1 <业务流一>
       ——参与模块、流转步骤（按顺序编号）、同步或异步方式、关键时序
   5.2 <业务流二>
       ——结构同 5.1

6. 接口与数据概要
   6.1 接口清单
       ——表格：接口编号、接口名称、提供方、调用方、用途、同步方式
   6.2 数据模型概要
       ——表格：实体、关键属性、与其他实体的关系
   6.3 存储方案概要
       ——存储类型、数据分类、容量与保留策略的概要
   6.4 数据流转
       ——数据从产生、加工到消费的路径

7. 非功能设计
   7.1 性能设计
   7.2 安全设计
   7.3 可靠性设计
   7.4 可维护性设计
   7.5 兼容性设计
       ——各节写明设计考虑与对应指标，无对应内容时删除该节

8. 风险与待定项
   ——表格：序号、风险或待定项、类型、影响、应对措施、需确认人、状态

9. 文档修订记录
   ——表格：版本、日期、修订内容、修订人，位于正文最后
```

结构约束：

- 全文编号连续，层级不超过四级；模块使用 `M-01` 编号，接口使用 `API-01` 编号，与 4.1、6.1 及正文保持一致。
- 1 章只写编写目的、设计范围、读者对象、术语，不写需求原文与技术实现细节。
- 2 章只写设计目标、约束与取舍，不写具体模块的内部实现。
- 3 章写系统组成、分层分区、部署形态、外部边界与选型理由，不写类图、函数签名、报文逐字段定义。
- 4 章先给模块清单，再按模块逐个展开；每个模块必须包含职责与边界、对外交互两节，不得缺节或合并；不写模块内函数级设计。
- 5 章按主要业务流组织，每条业务流写清参与模块与流转顺序；不写接口报文完整字段定义，字段级内容留到 6 章概要。
- 6 章只写接口与数据的概要，不写表结构逐字段定义、SQL 与报文编码细节。
- 7 章每项设计必须对应 PRD 中的非功能指标或约束，无对应指标的项不写。
- 8 章汇总设计风险与未定事项，每条写明影响范围、应对措施与需确认人；已被正文确定为结论的内容不重复列入。
- 9 章固定放在正文最后，不并入概述；每次修订追加一行，不覆盖历史记录。

## 写作规范

**设计表述**

- 每项设计写成可判定的陈述，说明「做什么、由哪个模块承担、如何交互」；架构与方案选择必须给出理由。
- 模块职责用「负责……」「不负责……」界定边界，同一职责不得分配给多个模块。
- 模块、接口、数据实体的名称全文统一，首次出现时给出定义。
- 同一设计约束在多处出现时，各章表述必须一致。

**内容边界**

- 不写类、函数、方法签名与代码片段。
- 不写数据库表结构逐字段定义、SQL、报文编码细节。
- 不写具体测试方案、测试数据与缺陷记录。
- 不出现「见 PRD 第 X 节」「详见详细设计」一类跨文档引用；可标注需求编号（如 F-003、NFR-002）用于追溯，但不得要求读者查阅 PRD。
- 架构图、时序图、部署图用文字、表格或缩进文本表达，不使用 mermaid。

**格式**

- 表格不嵌套，列表不嵌套。
- 文件为 UTF-8 编码，无 BOM。

## 输出

### 存放位置

```
docs/<项目或特性>/HLD-<名称>.md
```

与同项目其他文档的命名风格保持一致。

### frontmatter

文件顶部必须包含以下字段（字段名固定，供 `md2docx` 识别封面信息）：

```yaml
---
title: <项目或特性名称> 概要设计文档
doc-type: HLD
version: V1.0
author: <作者>
date: <YYYY-MM-DD>
confidentiality: 内部
cover: true
toc: true
---
```

取值规则：`author` 默认取 PRD 的修订人或使用者指定的人；`date` 取成文当天；首版 `version` 为 V1.0。确实无法确定时留空字符串，并列入第 8 章。

### 图片

- 架构图、部署图、时序图放在 md 文件同级的 `images/` 目录，命名 `hld-<章节号>-<序号>.png`，引用写法 `![图题](images/xxx.png)`。
- 没有可用的图片素材时，不写入指向不存在文件的图片引用，也不留空占位，改用文字、表格或缩进文本表达。

## 交付说明（仅在对话中输出，不写入文档）

交付文档时在对话中说明三项：

- **待确认清单**：与第 8 章一致，每条写明问题、影响范围与需确认人。
- **设计缺口**：列出 PRD 未覆盖但设计必须确定的问题（如部署形态、外部系统、性能约束），说明缺失影响哪一章节。
- **建议补充材料**：按章节列出建议补充的架构图、部署图、接口文档或运行环境说明；没有可用的材料时必须输出。

## 自检清单

**结构完整性**

- frontmatter 字段齐全且取值符合规则。
- 1~9 章齐全；4 章每个模块的两节齐全；8 章表格字段齐全。
- PRD 的每条功能需求在 4 章有模块落点，每条非功能要求在第 7 章有对应设计。

**内容准确性**

- 每项设计都能追溯到 PRD 的功能或非功能要求，无 PRD 之外的功能。
- 模块职责边界清晰、无重叠；模块之间的依赖方向明确。
- 架构与关键方案均有采用理由；接口清单的提供方、调用方、同步方式完整。
- 无类与函数签名、表结构逐字段定义、SQL、报文编码等实现细节。
- 无跨文档引用，不要求读者查阅 PRD。

**格式规范**

- 表格与列表均为单层，无嵌套；不使用 mermaid 或流程图代码块。
- 正文无「待确认」「TODO」等字样残留。
- 文件为 UTF-8 编码且无 BOM。
