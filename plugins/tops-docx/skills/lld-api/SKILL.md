# 接口设计说明书 (lld-api)

## 用途

撰写详细设计阶段的**接口设计说明书**，把业务交互与系统集成需求细化到可对接的粒度：接口协议与公共约定、请求与响应字段、错误码、超时重试与幂等约束、消息与事件、接口安全、版本兼容。

**本技能可以脱离 HLD 独立使用**：有 HLD 时从 HLD 的接口清单与模块交互推导；没有 HLD 时，从 PRD、现有接口文档、代码或使用者口述中取证。

本技能只负责接口设计内容，不写表结构、类与函数、模块内部流程、部署与运维。本技能只负责「写成 markdown」；需要 Word 文档时，由使用者再调用 `md2docx` 技能按 docx 模板转换。

## 触发条件

- 使用者要求「写接口设计」「写接口文档」「写接口设计说明书」「写报文定义」时使用。
- 使用者提供需求、HLD（如有）、现有接口文档或代码，并要求据此产出接口设计时使用。
- 使用者说 `/lld-api` 时使用。
- 只需要表结构或模块内部实现时，不使用本技能。

## 输入来源与证据优先级

按以下优先级取证，高优先级来源覆盖低优先级来源：

| 优先级 | 来源 | 用于确认 |
|--------|------|----------|
| 1 | 使用者当前在对话中提供的业务交互、集成需求、接口要点 | 接口范围、提供方与调用方、同步方式、数据对象 |
| 2 | 使用者指定路径的 HLD（如有）、PRD、现有系统设计文档 | 接口清单、模块交互、数据实体、非功能要求 |
| 3 | 现有接口文档、OpenAPI/Swagger、代码中的路由与 DTO、报文样例 | 字段名、类型、错误码、协议现状 |
| 4 | 使用者口述的补充说明与对接方约定 | 鉴权方式、超时、重试、限流、版本策略 |

**检索与降级规则**：

- **HLD 不是必需输入**。没有 HLD 时，直接按 PRD、现有接口文档、代码或使用者口述取证，不要求使用者先补 HLD。
- 优先使用使用者当前提供的形式；对话中已粘贴的内容不再重复读取文件。
- **不要求任何输入文件存在于固定路径**——本技能必须能脱离仓库中的文档独立成文。
- 文件可能因加密、损坏或格式不兼容而无法读取；读不到即降级取证，**不要根据文件名或常识臆测其内容**。
- 优先级 1~3 都拿不到足够的接口信息时，先向使用者索取必要输入；仅个别细节无法确认时，不中断成文。
- 现有代码或接口文档中存在但材料未覆盖的接口，不擅自写入正文，在交付对话中列出。
- 对接方约定与内部约定冲突时，以使用者当前确认的对外契约为准，差异在交付对话中说明。

## 工作流

1. 确认项目/特性名称、使用者指定的输出目录、覆盖范围（对外接口、内部接口、消息事件）与目标协议风格。
2. 从可用材料中提炼接口清单（`API-` 编号）及提供方、调用方；材料不足时按现有信息取最合理方案，不中断成文。
3. 确定公共约定（统一响应结构、时间与金额格式、分页、鉴权、幂等、版本前缀）和公共数据结构（`D-` 编号）；无法确认的按现有材料取最合理方案成文，并记入交付时的待确认清单。
4. 按「章节骨架」逐接口展开：请求、响应、错误码、调用约束；字段写到可直接编码的粒度。
5. 编写消息与事件、接口安全、版本与兼容。
6. 按「自检清单」逐项核对。
7. 交付时在对话中列出待确认项、设计缺口与建议补充材料，不写入文档。
8. 告知使用者将要写入的文件路径；目标文件已存在时先询问覆盖还是改名，确认后再写入。

## 冲突处理

- 使用者当前答复与既有文档不一致：以使用者当前答复为准，差异在交付对话中说明。
- 需求文档、HLD（如有）与现有接口实现不一致：以使用者确认的接口契约为准，代码只作实现参考；差异及处理方式在交付对话中说明。
- 字段名、类型或错误码在不同材料中冲突：以使用者确认的对外契约为准；仍无法判断时按现有材料取最合理方案成文，并在交付对话中列出。
- 协议、鉴权方式、超时、重试、限流、版本策略无法确认时按现有材料取最合理方案成文，并在交付对话中列出，写明对哪些接口有影响。

## 章节骨架

文档按下述多级章节组织，`<...>` 处按实际项目替换，`——` 后为该节应包含的内容。固定章节不得删减；项目无对应内容时删除该节并顺延编号，不留空节。

```
1. 文档概述
   1.1 编写目的
   1.2 设计范围
       ——覆盖的接口类型、协议与业务范围，以及明确不包含的部分
   1.3 读者对象
       ——表格：读者角色、关注内容
   1.4 术语与缩略语
       ——表格：术语/缩略语、全称或含义、说明
   1.5 编号与命名约定
       ——表格：编号前缀、对象、使用范围
       ——接口路径、字段名、错误码的命名规则与示例

2. 接口总体设计
   2.1 接口风格与协议
       ——REST/RPC/消息等风格，传输协议、编码、数据格式、版本前缀
   2.2 公共约定
       ——统一响应结构、时间与金额格式、字符编码、分页、排序、幂等键、空值约定
   2.3 接口清单
       ——表格：接口编号、接口名称、接口类型（对外/内部/消息）、提供方、调用方、协议、同步方式、版本
   2.4 接口与业务的对应关系
       ——表格：接口编号、承载业务、对应需求编号、说明

3. 公共数据结构
   3.1 公共结构清单
       ——表格：编号、名称、用途、使用接口
   3.2 <结构一>
       ——表格：字段名、类型、必填、含义、取值范围、约束
   3.3 <结构二>
       ——结构同 3.2
   3.N 公共枚举与常量
       ——表格：编号、名称、取值、含义

4. 接口详细设计
   4.1 <接口一>
       4.1.1 接口说明
           ——用途、提供方、调用方、触发场景、前置条件
       4.1.2 请求定义
           ——表格：字段名、类型、必填、含义、取值范围、约束
       4.1.3 响应定义
           ——表格：字段名、类型、必填、含义、取值范围、约束
       4.1.4 错误码
           ——表格：错误码、含义、触发条件、对外提示、可否重试
       4.1.5 调用约束
           ——超时、重试与退避、幂等、限流、鉴权、并发或顺序要求
       4.1.6 报文示例
           ——请求与响应示例，放在围栏代码块并标注 json；无示例时删除本节
   4.2 <接口二>
       ——结构同 4.1
   4.N <接口 N>
       ——结构同 4.1

5. 消息与事件设计
   5.1 主题与队列清单
       ——表格：消息编号、主题或队列名、生产方、消费方、消息类型、投递语义
   5.2 <消息一>
       5.2.1 消息说明
           ——用途、触发条件、生产与消费场景
       5.2.2 消息结构
           ——表格：字段名、类型、必填、含义、取值范围、约束
       5.2.3 投递与消费语义
           ——至少一次/至多一次/恰好一次，顺序性，重复消费处理
       5.2.4 重试与死信
           ——重试次数、退避策略、死信处理与人工补偿方式

6. 接口安全
   6.1 鉴权与授权
       ——鉴权方式、令牌或签名位置、权限粒度
   6.2 签名与加密
       ——签名算法、参与字段、密钥管理要求、传输加密
   6.3 限流与防重放
       ——限流维度与阈值来源、时间戳与随机数要求、防重放窗口
   6.4 审计与敏感数据
       ——审计字段、敏感字段的脱敏或加密要求

7. 版本与兼容
   7.1 版本策略
       ——版本标识方式、并行版本的支持周期
   7.2 向后兼容规则
       ——允许的变更（新增可选字段等）与禁止的变更（改字段含义、改类型等）
   7.3 废弃与下线
       ——废弃标记方式、通知周期、下线条件

8. 文档修订记录
   ——表格：版本、日期、修订内容、修订人，位于正文最后
```

结构约束：

- 全文编号连续，层级不超过四级。接口使用 `API-01`，数据结构使用 `D-01`，错误码使用 `ERR-01`，消息使用 `MSG-01`；同一对象在全文中只使用一个编号。
- 1.5 节只写本文档使用的编号前缀、命名规则与示例，不引入本文档之外的设计内容。
- 2 章写风格、公共约定与清单，不写单个接口的字段。
- 3 章只定义被两个及以上接口复用的数据结构；只被单个接口使用的结构直接在 4 章展开，不单独定义。
- 4 章先给接口清单（2.3），再按接口逐个展开。`4.x.1` 至 `4.x.5` 五节必须齐全，不得缺节或合并；`4.x.6` 报文示例有示例时保留，无示例时删除本节。
- 请求与响应定义必须写全：字段名、类型、必填、含义、取值范围、约束。嵌套结构用 `D-` 编号引用，不重复展开。
- 5 章按消息逐个展开，无消息或事件的系统删除整章并顺延编号。
- 6 章写接口安全要求，不写网关部署、证书申请与运维操作。
- 7 章写版本与兼容规则，不写具体发布计划。
- 8 章固定放在正文最后，不并入概述；每次修订追加一行，不覆盖历史记录。

## 写作规范

**设计表述**

- 每个字段写成可判定的定义：类型、必填、取值范围、约束齐全，不使用「字符串」「对象」这类模糊表述。
- 字段命名采用接口实际使用的风格（如 `snake_case` 或 `camelCase`），全文一致；同一含义的字段在不同接口中使用同一名称。
- 错误码全局唯一，按接口或业务域分段分配；错误码含义与触发条件必须可判定。
- 同一接口在多处出现时，各章表述必须一致。

**报文示例**

- 报文示例放在围栏代码块并标注 `json`，只用于表达结构，不写全量业务数据。
- 示例字段必须与 4.x.2、4.x.3 的字段表一致；两者冲突时以字段表为准并修正示例。
- 不粘贴完整的客户端或服务端实现代码。

**文档自洽**

- 本文档自成体系：接口、数据结构、错误码、消息均在本册内完整定义，不要求读者查阅其他设计文档或需求文档才能理解正文。
- 不写「见某文档第 X 节」「详见数据库设计/模块设计」一类跨文档引用；确需提及项目中的其他对象时，只写名称，不展开引用。

**内容边界**

- 不写表结构逐字段定义、建表 SQL 与数据库索引。
- 不写模块内部的类、函数、处理流程与异常策略。
- 不写部署架构、网关配置、证书管理与运维操作。
- 不写具体测试用例、测试数据与缺陷记录。

**格式**

- 时序图、状态图用编号步骤、表格或缩进文本表达，不使用 mermaid。
- 表格不嵌套，列表不嵌套。
- 文件为 UTF-8 编码，无 BOM。

## 输出

### 存放位置

```
docs/<项目或特性>/LLD-接口设计.md
```

使用者指定目录时以使用者指定为准；同项目的文档命名风格保持一致。

### frontmatter

文件顶部必须包含以下字段（字段名固定，供 `md2docx` 识别封面信息）：

```yaml
---
title: <项目或特性名称> 接口设计说明书
doc-type: LLD
doc-part: API
version: V1.0
author: <作者>
date: <YYYY-MM-DD>
confidentiality: 内部
cover: true
toc: true
---
```

取值规则：`doc-part` 固定为 `API`；`author` 默认取使用者指定的人或需求文档的修订人；`date` 取成文当天；首版 `version` 为 V1.0。确实无法确定时留空字符串，并在交付对话中说明。

### 图片

- 接口时序图、状态图放在 md 文件同级的 `images/` 目录，命名 `lld-api-<章节号>-<序号>.png`，引用写法 `![图题](images/xxx.png)`。
- 没有可用的图片素材时，不写入指向不存在文件的图片引用，也不留空占位，改用编号步骤或表格表达。

## 交付说明（仅在对话中输出，不写入文档）

交付文档时在对话中说明三项：

- **待确认清单**：列出成文过程中未能确定、按假设写入的事项，每条写明当前采用的假设、依据、影响范围与需确认人。
- **设计缺口**：列出材料未覆盖但对接口对接必须确定的问题（如鉴权方式、超时取值、限流阈值、错误码分段、版本策略、消息投递语义），说明缺失影响哪一章节。
- **建议补充材料**：按章节列出建议补充的现有接口文档、OpenAPI 定义、报文样例、对接方约定或安全规范；没有可用的材料时必须输出。

## 自检清单

**结构完整性**

- frontmatter 字段齐全且取值符合规则。
- 1~8 章齐全（无消息时 5 章按规则删除并顺延编号）；4 章每个接口的 `4.x.1`~`4.x.5` 齐全。
- 已识别的接口在 2.3 与 4 章有落点。

**内容准确性**

- 每个请求、响应、消息字段的类型、必填、含义、取值范围、约束齐全，无「待补充」。
- 错误码全局唯一，触发条件可判定；调用约束写明超时、重试与幂等。
- 公共数据结构只定义一次，其余位置按 `D-` 编号引用。
- 报文示例与字段表一致。
- 无表结构、模块内部实现、部署与运维内容。

**格式规范**

- 表格与列表均为单层，无嵌套；不使用 mermaid 或流程图代码块。
- 编号连续，无重复；不出现跨文档引用。
- 正文无「待确认」「TODO」等字样残留。
- 文件为 UTF-8 编码且无 BOM。
