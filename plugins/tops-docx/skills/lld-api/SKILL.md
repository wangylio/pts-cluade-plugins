# 接口设计说明书 (lld-api)

## 用途

撰写**接口设计说明书**，把业务交互与系统集成需求细化到可对接的粒度：接口协议与公共约定、请求与响应字段、错误码、超时重试与幂等、消息与事件、接口安全。

- 有 HLD 时从 HLD 的接口清单与模块交互推导；没有 HLD 时，从 PRD、现有接口文档、代码或使用者口述取证。
- 只写接口设计，不写表结构、模块内部实现、部署与运维。

## 触发条件

- 要求「写接口设计」「写接口文档」「写接口设计说明书」「写报文定义」，或输入 `/lld-api` 时使用。
- 只需要表结构或模块内部实现时，不使用本技能。

## 输入来源

按优先级取证，高优先级覆盖低优先级：

1. 对话中提供的业务交互、集成需求、接口要点与对接方约定（鉴权、超时、重试、限流）。
2. HLD（如有）、PRD、现有系统设计文档。
3. 现有接口文档、OpenAPI/Swagger、代码中的路由与 DTO、报文样例。

规则：

- 输入不要求位于固定路径；读不到即降级取证，不按文件名或常识臆测内容。
- 材料不足时按现有信息取最合理方案成文，不中断；未定项列入交付对话的待确认清单。
- 使用者当前答复与既有文档、代码冲突时，以使用者确认的对外契约为准，差异在交付对话中说明。
- 现有代码或接口文档中存在、但材料未覆盖的接口，不擅自写入正文，在交付对话中列出。

## 工作流

1. 确认项目/特性名称、输出目录、覆盖范围（对外接口、内部接口、消息事件）与目标协议风格。
2. 提炼接口清单（`API-` 编号）及提供方、调用方。
3. 确定公共约定（统一响应结构、时间与金额格式、分页、排序、幂等键、版本前缀）与接口安全要求；项目不涉及的细则不写。
4. 按「章节骨架」逐接口展开，字段写到可直接编码的粒度。
5. 编写消息与事件，并按「自检清单」核对。
6. 交付：待确认项、设计缺口与建议补充材料，并告知文件路径。

目标文件已存在时，先询问覆盖还是改名。

## 章节骨架

`<...>` 按实际项目替换，`——` 后为该节内容。固定章节不得删减；项目无对应内容时删除该节并顺延编号，不留空节。

```
1. 文档概述
   1.1 编写目的
   1.2 设计范围 —— 覆盖的接口类型、协议与业务范围；明确不包含的部分
   1.3 读者对象 —— 表格：读者角色、关注内容
   1.4 术语与缩略语 —— 表格：术语/缩略语、含义、说明
   1.5 编号与命名约定 —— 编号前缀表；接口路径、字段名、错误码的命名规则与示例

2. 接口总体设计
   2.1 接口风格与协议 —— REST/RPC/消息等风格，传输协议、编码、数据格式、版本前缀
   2.2 公共约定 —— 统一响应结构、时间与金额格式、分页、排序、幂等键、空值约定
   2.3 接口清单 —— 表格：接口编号、名称、请求方式、路径、类型（对外/内部/消息）、提供方、调用方、协议、同步方式、版本

3. 接口安全
   3.1 鉴权与授权 —— 鉴权方式、令牌或签名位置、权限粒度
   3.2 签名与加密 —— 签名算法、参与字段、密钥管理要求、传输加密
   3.3 限流与防重放 —— 限流维度与阈值来源、时间戳与随机数要求、防重放窗口
   3.4 审计与敏感数据 —— 审计字段、敏感字段的脱敏或加密要求

4. 接口详细设计
   4.1 <接口一>
       4.1.1 接口说明 —— 用途、请求方式、服务地址、路径、提供方、调用方、触发场景、前置条件
       4.1.2 请求定义 —— 表格：字段名、类型、必填、含义、取值范围、约束
       4.1.3 响应定义 —— 表格：字段名、类型、必填、含义、取值范围、约束
       4.1.4 错误码 —— 表格：错误码、含义、触发条件、对外提示、可否重试
       4.1.5 调用约束 —— 超时、重试与退避、幂等、限流、鉴权、并发或顺序要求
       4.1.6 报文示例 —— 请求报文示例与响应报文示例各一段 json 代码块，字段齐全、可直接对接；无示例时删除本节
   4.2 <接口二> —— 结构同 4.1
   4.N <接口 N> —— 结构同 4.1

5. 消息与事件设计
   5.1 主题与队列清单 —— 表格：消息编号、主题或队列名、生产方、消费方、消息类型、投递语义
   5.2 <消息一>
       5.2.1 消息说明 —— 用途、触发条件、生产与消费场景
       5.2.2 消息结构 —— 表格：字段名、类型、必填、含义、取值范围、约束
       5.2.3 投递与消费语义 —— 至少一次/至多一次/恰好一次，顺序性，重复消费处理
       5.2.4 重试与死信 —— 重试次数、退避策略、死信处理与人工补偿方式

6. 文档修订记录 —— 表格：版本、日期、修订内容、修订人，位于正文最后
```

结构要求：

- 全文编号连续，层级不超过四级。接口用 `API-01`、错误码用 `ERR-01`、消息用 `MSG-01`；同一对象全文只用一个编号。
- 2 章只写风格、公共约定与清单，不写单个接口的字段。
- 3 章只写项目实际涉及的安全细则，不涉及的整节删除；不写网关部署、证书申请与运维操作。
- 4 章每个接口的 `4.x.1`~`4.x.5` 必须齐全，不得合并；嵌套结构在字段表中展开说明，不跨章节引用。
- 每次修订在修订记录中追加一行，不覆盖历史记录。

## 写作规范

- 字段的类型、必填、含义、取值范围、约束必须齐全，不使用「字符串」「对象」这类模糊表述。
- 字段命名采用接口实际使用的风格（`snake_case` 或 `camelCase`），全文一致；同一含义用同一名称。
- 错误码全局唯一，按接口或业务域分段；含义与触发条件必须可判定。
- 报文示例分为请求报文示例与响应报文示例，每段都是完整报文：字段与 4.x.2、4.x.3 的字段表一致，必填字段与嵌套层次全部给出，不用省略号或注释占位；冲突时以字段表为准。
- 文档自成体系，不写「见某文档第 X 节」一类跨文档引用。
- 不写测试用例、缺陷记录与实现代码。
- 时序图、状态图用编号步骤或表格表达，不使用 mermaid；表格与列表不嵌套。

## 输出

输出路径由使用者指定。文件顶部必须包含以下字段：

```yaml
---
title: <项目或特性名称> 接口设计说明书
doc-type: LLD
doc-part: API
version: V1.0
author: <作者>
date: <YYYY-MM-DD>
confidentiality: 内部
cover: true
toc: true
---
```

`doc-part` 固定为 `API`；`author` 取使用者指定的人或需求文档的修订人；`date` 取成文当天；首版 `version` 为 V1.0。无法确定时留空，并在交付对话中说明。

## 交付说明（仅对话输出，不写入文档）

- **待确认清单**：未能确定、按假设写入的事项，每条写明当前假设、依据、影响范围与需确认人。
- **设计缺口**：材料未覆盖但对接口对接必须确定的问题（如鉴权方式、超时取值、限流阈值、错误码分段、消息投递语义），说明影响哪一章节。
- **建议补充材料**：现有接口文档、OpenAPI 定义、报文样例、对接方约定或安全规范；没有时必须说明。

## 自检清单

- frontmatter、章节与编号齐全连续；3 章无空节；接口在 2.3 与 4 章均有落点，每个接口 `4.x.1`~`4.x.5` 齐全。
- 字段的类型、必填、含义、取值范围、约束完整，无「待补充」；每个接口都写明请求方式、服务地址与路径；请求与响应报文示例齐全，字段与字段表一致且无省略占位，嵌套结构展开完整。
- 错误码唯一且触发条件可判定；调用约束写明超时、重试与幂等；无跨文档引用与越界内容。
- 表格与列表不嵌套，不使用 mermaid；正文无「待确认」「TODO」；文件为 UTF-8 无 BOM。
