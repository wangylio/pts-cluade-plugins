# 需求分析文档集（多文档版 prd-suite）

## 用途

撰写面向研发、测试与项目干系人的**需求分析文档（PRD）**：由一份**总册**描述系统整体需求，由若干份**分册**分别描述每个功能迭代的需求，输出为 UTF-8 编码的 markdown 文件。

本技能适用于大型系统或功能较多、需求按迭代分批交付的系统。使用者要求把需求拆成「总体 + 各迭代」多份文档时，使用本技能。

本技能只负责「写成 markdown」。需要 Word 文档时，由使用者再调用 `md2docx` 技能按 docx 模板转换。

## 触发条件

- 使用者要求「写产品需求文档」「写 PRD」「整理需求文档」，并说明需求分成总体文档与多份迭代文档时使用。
- 使用者提供多批次、多迭代的需求材料，要求产出成套需求文档时使用。
- 使用者说 `/prd-suite` 时使用。

## 输入来源与证据优先级

需求内容只来自使用者答复与使用者提供的材料。按以下优先级取证，高优先级来源覆盖低优先级来源：

| 优先级 | 来源 | 用于确认 |
|--------|------|----------|
| 1 | 使用者对提问的明确答复 | 系统目标、迭代划分、范围边界、业务规则、数值指标、验收标准 |
| 2 | 使用者提供的需求材料：会议纪要、任务单、原型稿、旧版文档、客户邮件、迭代计划 | 业务背景、角色职责、流程步骤、字段与规则细节 |
| 3 | 现有系统：实现代码、界面、配置 | 现状与存量规则（仅作参照，不直接视为新需求） |
| 4 | 行业惯例与同类产品 | 只用于提出问题，不得直接写入文档 |

**检索与降级规则**：

- 先按提问补齐信息，再查阅使用者提供的材料；材料只作为线索，最终以使用者答复为准。
- 材料可能因加密、损坏或格式不兼容而无法读取；读不到即降级取证，**不要根据文件名或常识臆测其内容**。
- 查不到且必须写入的内容，登记到对应文档的第 8 章；不得以行业惯例替代使用者确认。
- 提问一次问一组相关问题，得到答复后再问下一组；使用者明确说「先按这个写」时，可在正文写已确认部分，未确认部分登记到第 8 章。

## 文档集构成

一套文档集由总册与分册组成，存放在同一目录（默认 `docs/01 prd/`）：

```
docs/01 prd/
├── 0101-需求分析文档-总体.md               # 总册
├── 010101-需求分析文档-<迭代或功能1>.md    # 分册
├── 010102-需求分析文档-<迭代或功能2>.md    # 分册
└── images/
```

| 文档 | 职责 | 不写的内容 |
|------|------|------------|
| 总册 | 系统级背景、目标、范围；角色与端到端场景；功能全景与分册归属；全局业务规则；非功能需求；外部依赖与约束；总体验收；文档集索引 | 各功能的业务流程、输入输出、业务规则与异常细节 |
| 分册 | 单个迭代或功能组的背景、目标、范围；相关角色与场景；功能详细需求（五节结构）；迭代特有非功能要求与验收 | 系统级背景与目标；系统级非功能指标；其他分册的功能 |

**划分规则**：

- 一份分册对应一次迭代或一个相对独立的业务功能组，边界由使用者确定。
- 分册数量、先后顺序与迭代或功能名由使用者确认；不得自行拆分或合并。
- 分册序号为两位数字（`01`、`02`……），按使用者确认的迭代顺序分配，一经使用不复用。
- 总册文档编号为 `0101`；分册文档编号为 `0101` 后接分册序号，即 `010101`、`010102`……；文档编号与文件名前缀一致。

**编号规则**：

- 功能需求：`F-<分册序号>-<三位序号>`，如 `F-01-001`；分册序号即分册文档编号 `0101<分册序号>` 的后两位，同一分册内连续编号。
- 非功能需求：总册为 `NFR-<三位序号>`；分册特有的为 `NFR-<分册序号>-<三位序号>`。
- 总册 4.1 的功能清单包含全部分册的功能编号；每份分册 4.1 只列本分册的功能编号。
- 编号在文档集内唯一，停用后不回收。

**跨文档引用规则**：

- 同一套文档之间允许引用，引用时使用**文档编号 + 需求编号**（如「见 0101 的 NFR-003」「见 010101 的 F-01-002」）。
- 非编号内容（如验收方式、术语）需要引用时，写**文档编号 + 章节号**（如「见 010102 的 7.3」）。
- 不得引用本套文档以外的任何文档。

## 工作流

1. 确认系统名称、文档集目录（默认 `docs/01 prd/`）与文档基准版本。
2. 与使用者确认分册划分：每份分册对应的迭代或功能组、先后顺序与迭代或功能名；不确定时先提问，不自行假定。
3. 先完成总册：按「输入来源与证据优先级」逐组提问，确认系统背景、目标、范围、角色、系统级场景、非功能需求、约束与验收方式；同时确定全部功能的编号与分册归属，形成 1.5 文档组成与 4.1 功能清单。
4. 按分册顺序逐份完成分册：每份先确认本迭代的范围与目标，再按功能逐个收集业务流程、规则、异常情况。
5. 每完成一份分册，回填总册 1.5 文档组成中该分册的状态与版本；功能归属或编号有变化时同步更新总册 4.1、4.2。
6. 全部文档成文后按「自检清单」核对整套文档，再向使用者交付。
7. 告知使用者将要写入的全部文件路径；目标文件已存在时先询问覆盖还是改名，确认后再写入。

## 增量维护

使用者只要求新增或修订某一迭代时，按下列方式处理，不重写整套文档：

- **新增分册**：确认新的分册序号、文档编号与功能编号范围，完成分册成文，然后同步更新总册的 1.5 文档组成、4.1 功能清单、4.2 功能分组与迭代划分、9 修订记录。
- **修订分册**：只改分册内容，同步更新该分册的 4.1、7.1、9 修订记录与总册 1.5 中该分册的版本、状态；影响系统范围、功能清单或非功能需求时，同步修订总册并记录。
- **功能跨分册迁移**：原编号停用并保留记录，迁移后的功能在新分册启用新编号；两份分册的修订记录与总册 4.1 同时说明。
- **删除功能**：总册 4.1、对应分册的 4.1 与 7.1 同步删除该功能，修订记录中说明停用编号，编号不回收。

## 冲突处理

- 使用者前后答复不一致：以最新答复为准，差异及采用的版本列入对应文档的第 8 章。
- 使用者答复与所提供材料不一致：以答复为准，材料中的差异列入对应文档的第 8 章。
- 总册与分册对同一功能的范围、编号或名称不一致：先与使用者确认，确认前不写入正文，差异登记到两份文档的第 8 章。
- 数值类争议（阈值、时限、数量、比例）无法确认：正文不写死具体数值，只写已确认的行为，数值争议列入对应文档的第 8 章。
- 不得自行补全业务规则、角色或指标；查不到的内容统一登记到第 8 章。

## 总册章节骨架

`<...>` 处按实际项目替换，`——` 后为该节应包含的内容。固定章节不得删减；项目无对应内容时删除该节并顺延编号，不留空节。

```
1. 文档概述
   1.1 编写目的
   1.2 适用范围
       ——系统覆盖的业务环节与功能范围，以及明确不包含的部分
   1.3 读者对象
       ——表格：读者角色、关注内容
   1.4 术语与缩略语
       ——表格：术语/缩略语、全称或含义、说明
   1.5 文档组成
       ——表格：文档编号、文档名称、文件名、内容范围、需求编号范围、版本、状态

2. 背景与目标
   2.1 业务背景
   2.2 当前问题
       ——问题清单：问题、表现、影响
   2.3 建设目标
       ——可判定的系统级目标，逐条编号
   2.4 范围边界
       ——本次明确不做的内容

3. 用户与场景
   3.1 用户角色
       ——表格：角色、职责、使用系统的环节
   3.2 系统级使用场景
       ——跨分册的端到端主流程，按业务发生顺序编号

4. 功能全景
   4.1 功能清单
       ——表格：需求编号、功能名称、功能说明、优先级、所属分册
   4.2 功能分组与迭代划分
       ——按业务域说明功能分组、每组承载的分册与迭代先后关系
   4.3 全局业务规则
       ——跨功能、跨分册统一的规则；仅单个分册适用的规则写在该分册

5. 非功能需求
   5.1 性能要求
       ——表格：指标项、指标值、适用场景
   5.2 兼容性要求
   5.3 安全性要求
   5.4 可靠性与可用性要求

6. 约束与依赖
   6.1 外部系统依赖
       ——表格：系统名称、依赖内容、提供方与可用条件
   6.2 政策与标准约束
   6.3 环境约束
       ——硬件、网络、部署环境限制

7. 验收标准
   7.1 总体功能验收
       ——表格：需求编号或验收项、验收条件；覆盖端到端流程与跨分册的功能组合
   7.2 非功能验收
       ——表格：指标项、验收条件，与 5 章一一对应
   7.3 验收方式
       ——验收组织、验收环境、判定依据

8. 待确认事项
   ——表格：序号、待确认问题、依据、需确认人、影响范围、状态

9. 文档修订记录
   ——表格：版本、日期、修订内容、修订人，位于正文最后
```

总册结构约束：

- 1 章只写编写目的、适用范围、读者对象、术语与文档组成，不写具体需求内容。
- 2 章只写系统级背景、问题、目标与边界，不写实现方式与界面设计。
- 3 章只写角色职责与系统级场景，不写页面布局与单个功能的操作步骤。
- 4.1 是全系统功能编号的唯一登记处；4.2 说明每份分册的承载范围与迭代顺序；4.3 只写跨分册复用的规则。
- 5 章按指标类别写系统级数值或判定条件，不写达成这些指标的技术手段；分册特有的指标不在总册重复。
- 7.1 只写跨分册的端到端验收与功能组合验收；单个功能的验收条件写在分册。
- 8、9 章与分册各自独立，汇总总册自身的未确认事项与修订记录。

## 分册章节骨架

```
1. 文档概述
   1.1 编写目的
   1.2 适用范围
       ——本分册覆盖的功能范围与不包含部分，以及对应总册的功能编号范围
   1.3 读者对象
       ——表格：读者角色、关注内容
   1.4 术语与缩略语
       ——只列本分册新增且未在总册登记的术语；跨分册使用的术语回填总册 1.4

2. 迭代背景与目标
   2.1 迭代背景
       ——本迭代的驱动原因与在系统中的位置
   2.2 当前问题
       ——问题清单：问题、表现、影响
   2.3 迭代目标
       ——可判定的目标，逐条编号
   2.4 范围边界
       ——本迭代明确不做的内容

3. 用户与场景
   3.1 用户角色
       ——只列本分册涉及的角色；职责已在总册写明的，只写角色名称与本分册的使用环节
   3.2 典型使用场景
       ——按业务发生顺序编号，每条写明触发条件、参与角色与期望结果

4. 功能需求
   4.1 功能清单
       ——表格：需求编号、功能名称、功能说明、优先级，编号与总册 4.1 一致
   4.2 <功能一>
       4.2.1 业务描述
       4.2.2 业务流程
           ——按操作顺序编号的步骤，标明参与角色
       4.2.3 输入与输出
           ——表格：名称、来源/去向、规则
       4.2.4 业务规则
           ——表格：条件、规则、结果
       4.2.5 异常与边界
           ——异常场景、判定条件、处理结果
   4.3 <功能二>
       ——结构同 4.2
   4.N <功能 N>
       ——结构同 4.2

5. 非功能要求
   ——只写本迭代特有的指标，表格：指标项、指标值、适用场景
   ——无特有指标时写明「本迭代无新增非功能要求，遵循 0101 的第 5 章」

6. 约束与依赖
   ——只写本迭代特有的依赖与约束；无时写明「本迭代无特有的约束与依赖」

7. 验收标准
   7.1 功能验收
       ——表格：需求编号、验收条件，与 4.1 一一对应
   7.2 非功能验收
       ——表格：指标项、验收条件；无本迭代特有指标时删除本节
   7.3 验收方式
       ——本分册的验收组织、环境与判定依据；与总册一致时写明「同 0101 的验收方式」

8. 待确认事项
   ——表格：序号、待确认问题、依据、需确认人、影响范围、状态

9. 文档修订记录
   ——表格：版本、日期、修订内容、修订人，位于正文最后
```

分册结构约束：

- 每份分册可独立交付：读者只拿到一份分册时，应能理解本迭代的范围与全部功能需求。
- 4 章每个功能必须包含业务描述、业务流程、输入与输出、业务规则、异常与边界五节，不得缺节或合并；不写数据库设计、接口报文与类函数设计。
- 分册不重复总册已写明的系统级背景、建设目标、角色职责与非功能指标。
- 分册内编号必须与总册 4.1 完全一致（编号、名称、优先级）；发现不一致时先向使用者确认。

## 文档集一致性规则

- **单一权威来源**：总册是系统范围、术语、角色、功能编号与非功能需求的唯一权威来源；每份分册是各自功能详细规则的唯一权威来源。
- **不重复表述**：同一内容只写一处。总册不展开功能细节，分册不重复系统级内容；确需提及总册已有内容时，用文档编号与需求编号引用，不复制正文。
- **清单对齐**：总册 4.1 的功能清单等于各分册 4.1 的并集（编号、名称、优先级一致）；1.5 文档组成中的文档编号、文件名、需求编号范围与版本与实际文件一致。
- **验收覆盖**：总册 7.1 覆盖跨分册端到端验收；每份分册的每个功能在分册 7.1 有验收条件。
- **术语统一**：角色、功能、状态、字段的名称在总册与全部分册中一致；分册新增且跨分册使用的术语回填总册 1.4。
- **版本独立**：各文档版本独立演进；分册修订不影响系统范围、功能清单或非功能需求时，不改总册版本。

## 写作规范

**需求表述**

- 每条需求写成可判定的陈述句，包含触发条件、处理行为与结果；避免「尽量」「友好」「快速」「完善」等不可验证的表述。
- 数值、时限、数量、比例必须有明确取值；无法确认的取值不写死，登记到对应文档的第 8 章。
- 角色、功能、状态、字段的名称全文统一，首次出现时给出定义；跨分册首次出现的术语以总册定义为准。
- 同一规则在多处出现时，各文档表述必须一致；无法避免重复时，以权威来源文档为准。

**内容边界**

- 不写界面布局、控件位置与视觉样式；界面细节由原型或 UI 稿承载。
- 不写数据库表名、字段名、接口报文、类与函数设计。
- 不出现「见需求讨论记录」「详见设计文档」一类跨文档引用；本套文档内部引用必须写文档编号加需求编号或章节号。
- 不出现「同前」「见上文」等依赖阅读顺序的表述。
- 用例图、流程图用编号列表或文字描述，不使用 mermaid。

**格式**

- 表格不嵌套，列表不嵌套。
- 文件为 UTF-8 编码，无 BOM。

## 输出

### 存放位置与命名

文档集存放在同一目录，默认 `docs/01 prd/`；使用者另行指定时按指定目录。

```
docs/01 prd/
├── 0101-需求分析文档-总体.md               # 总册
├── 010101-需求分析文档-<迭代或功能1>.md    # 分册
├── 010102-需求分析文档-<迭代或功能2>.md    # 分册
└── images/
```

- 总册文件名固定为 `0101-需求分析文档-总体.md`。
- 分册文件名为 `0101<两位分册序号>-需求分析文档-<迭代或功能名>.md`，如 `010101-需求分析文档-订单创建.md`。
- 迭代或功能名使用简短、可辨识的中文名称，与总册 1.5 文档组成中的登记一致。

### frontmatter

每份文档顶部都必须包含以下字段（字段名固定，供 `md2docx` 识别封面信息）。文档名称统一使用「需求分析文档」；总册的 `title` 加「（总体）」后缀，分册的 `title` 加迭代或功能名称。

```yaml
---
title: <系统名称> 需求分析文档（总体）
doc-type: PRD
version: V1.0
author: <作者>
date: <YYYY-MM-DD>
confidentiality: 内部
cover: true
toc: true
---
```

```yaml
---
title: <系统名称> 需求分析文档（<迭代或功能名>）
doc-type: PRD
version: V1.0
author: <作者>
date: <YYYY-MM-DD>
confidentiality: 内部
cover: true
toc: true
---
```

取值规则：`author` 默认取使用者指定的人；`date` 取该文档成文当天；首版 `version` 为 V1.0。确实无法确定时留空字符串，并列入该文档第 8 章。

### 图片

- 原型图、示意图统一放在文档集目录下的 `images/` 中，避免各文档建立相互独立的目录。
- 总册图片命名 `0101-<章节号>-<序号>.png`；分册图片命名 `<分册文档编号>-<章节号>-<序号>.png`，如 `010103-4.2-01.png`；引用写法 `![图题](images/xxx.png)`。
- 没有可用的图片素材时，不写入指向不存在文件的图片引用，也不留空占位。

## 交付说明（仅在对话中输出，不写入文档）

交付文档集时在对话中说明四项：

- **文档清单**：总册与各分册的文档编号、文件路径、版本、覆盖的需求编号范围。
- **待确认清单**：合并各文档第 8 章的内容，按文档分组，每条写明问题、依据、需确认人与影响范围。
- **资料缺口**：列出使用者未提供且影响需求完整性的信息（如性能指标、外部系统依赖、迭代排期、验收组织方式），说明缺失影响哪份文档的哪一章节。
- **跨文档不一致项**：列出尚未解决的编号、名称或范围冲突，写明涉及哪些文档与需求编号。

## 自检清单

**结构完整性**

- 总册与每份分册的 frontmatter 字段齐全且取值符合规则。
- 总册 1~9 章齐全，含 1.5 文档组成；每份分册 1~9 章齐全，4 章每个功能的五节齐全。
- 总册 1.5 列出的文档编号、文件名、版本与实际文件一致；总册 4.1 的功能清单等于各分册 4.1 的并集。
- 每份分册的每个功能在分册 7.1 有验收条件；总册 7.1 覆盖跨分册的端到端验收。

**内容准确性**

- 所有业务规则、角色、指标、验收条件均能追溯到使用者答复或指定材料，无编造。
- 总册与分册之间无重复展开的内容；同一名称、编号、规则在各文档中表述一致。
- 无「尽量」「友好」「快速」等不可验证表述；数值均有明确取值或已登记到第 8 章。
- 跨文档引用只使用文档编号加需求编号或章节号，无套外引用，无数据库表名、接口报文、类与函数设计。

**格式规范**

- 表格与列表均为单层，无嵌套；不使用 mermaid 或流程图代码块。
- 各文档正文无「待确认」「TODO」等字样残留。
- 每份文档可独立阅读；文件均为 UTF-8 编码且无 BOM。
