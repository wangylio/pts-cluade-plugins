# 发版升级说明 (rl)

## 用途

撰写面向运维、实施与研发的**发版升级说明**，说明本次升级改了什么、升级前要检查什么、按什么顺序执行、如何验证、出问题如何回滚，并把升级所需的脚本（数据库变更、校验、执行编排、回滚等）按类别分别落盘，确保拿到文件的执行人可直接按文档操作。

- 一次发版对应一份说明，说明与脚本放在同一个以发版日期命名的子文件夹下。
- 只写本次升级需要的内容，不写与升级无关的功能介绍、设计论证与完整测试用例。
- 只输出 markdown 与脚本；说明文档需要 Word 版本时，由使用者再调用 `md2docx` 技能转换。

## 触发条件

- 要求「写发版说明」「写升级说明」「整理升级脚本」「准备上线/发版材料」时使用。
- 使用者给出变更清单、版本号或发布包，要求输出升级步骤与脚本时使用。
- 使用者说 `/rl` 时使用。

## 输入来源与证据优先级

按以下优先级取证，高优先级来源覆盖低优先级来源：

| 优先级 | 来源 | 用于确认 |
|--------|------|----------|
| 1 | 使用者对提问的明确答复 | 版本号、发版日期、升级窗口、是否停机、执行环境与账号、回滚要求 |
| 2 | 本次变更材料：变更单、发布单、需求/缺陷编号、代码 diff、git 提交记录、发布包说明 | 升级内容、影响模块、表结构与配置变更、脚本需求 |
| 3 | 现有系统：实现代码、配置文件、DDL、历史发版说明、部署与运维手册 | 命令格式、部署路径、服务名、健康检查方式、历史脚本写法 |
| 4 | 行业惯例与通用运维实践 | 只用于提出检查项，不得据此臆造表名、字段、命令或路径 |

**检索与降级规则**：

- 脚本中的表名、字段名、命令、路径必须有出处（设计文档、DDL、代码、配置文件或使用者确认）；查不到就问，不猜。
- 材料可能因加密、损坏或格式不兼容而无法读取；读不到即降级取证，**不要根据文件名或常识臆测其内容**。
- 查不到但必须写入的内容先向使用者确认，确认后再写入；未确认前不写入正文，只在交付对话中列出，不得用通用示例冒充实际脚本。
- 使用者要求「先出框架」时，可先成文，未定项不写入正文，集中列入交付对话的待确认事项；脚本只保留确有必要留待填写的配置变量。

## 工作流

1. 确认发版信息：系统/项目名称、目标版本、当前版本、发版（升级）日期、输出根目录（默认 `docs/05 rl/`）、使用者是否要求重新创建。
2. 检查根目录下的日期子文件夹，判定本次是**新建**还是**修订**（见「目录与新建/修订判定」），确定本次子文件夹。
3. 收集变更清单，逐条判定是否涉及数据库、配置、程序包、外部依赖，整理出脚本需求。
4. 先定脚本清单（0~N 个，每类一个），再写脚本内容；没有该类变更就不生成该文件。
5. 按「章节骨架」成文，保证脚本清单、执行步骤、脚本头注释三者一致。
6. 按「自检清单」逐项核对后交付；修订模式下只改动需要变更的部分。

## 目录与新建/修订判定

默认根目录为 `docs/05 rl/`，使用者另行指定时以指定目录为准。子文件夹以**发版（升级）日期**命名，格式 `YYYY-MM-DD`；使用者未指定日期时取调用当天。

```
docs/05 rl/
└── 2026-11-26/
    ├── 发版升级说明.md
    ├── check.sql
    ├── upgrade.sql
    ├── verify.sql
    ├── upgrade.sh
    └── rollback.sql
```

判定规则：

1. 根目录下不存在目标日期子文件夹 → **新建**，把本次说明与全部脚本放入该文件夹。
2. 已存在目标日期子文件夹，且使用者未要求重新创建 → **修订模式**：读取已有的 `发版升级说明.md` 与全部脚本，在原有内容上补充、修改；不新建文件夹，不覆盖删除已有脚本文件。
3. 使用者明确要求「重新创建」「重新生成」「另出一份」→ 新建 `<日期>-2` 子文件夹；已被占用则递增为 `<日期>-3`、`<日期>-4`。
4. 同一日期下确属不同版本或不同升级批次，且使用者要求分开存放 → 同样按第 3 条新建带后缀的文件夹。
5. 无法判断是新建还是修订时，先向使用者确认一句，不默认新建；已有说明的目标版本与本次目标版本不一致时，同样先确认是修订已有版本还是新建批次。

修订模式规则：

- 先读后写：先读现有的说明与全部脚本，保留与本次补充无关的已确认内容。
- 只改使用者要求变更的部分；需要连带修改的步骤号、执行命令、脚本头注释一并同步。
- 已有类别的脚本原地修改；只有出现新类别时才新增文件。
- 不改写历史修订记录，在第 8 章追加一行；frontmatter 的文档版本同步递增。
- 修订完成后重新执行自检，交付时只列改动点，不复述整篇内容。

## 章节骨架

`<...>` 处按实际项目替换，`——` 后为该节应包含的内容。固定章节不得删减；项目无对应内容时删除该节并顺延编号，不留空节。

```
1. 升级概述
   1.1 基本信息
       ——表格：系统名称、目标版本、当前版本、发版日期、升级窗口、是否停机、影响范围、升级负责人
   1.2 脚本清单
       ——表格：序号、脚本文件、类别、用途、执行顺序、执行命令、是否可重复执行、对应回滚脚本

2. 升级内容
   2.1 变更清单
       ——表格：编号、变更类型（新增/修改/优化/修复）、变更内容、影响模块或服务、关联需求或缺陷编号、是否涉及数据库、是否涉及配置
   2.2 升级影响说明
       ——受影响功能、对外接口兼容性、数据兼容性、需业务方配合的事项

3. 前置检查
   3.1 环境检查
       ——表格：检查项、检查方法或命令、预期结果、不满足时的处理
   3.2 数据与备份检查
       ——数据量评估、大表变更耗时预估、备份方式与备份位置、备份校验方法
   3.3 权限与依赖检查
       ——执行账号及所需权限、依赖服务/中间件/外部系统可用性

4. 升级执行顺序
   4.1 执行步骤总览
       ——表格：步骤、操作、执行脚本或命令、预期结果、失败处理
   4.2 <步骤一>
       ——操作说明、执行命令、预期输出、校验方法、耗时预估
   4.N <步骤 N>
       ——结构同 4.2

5. 冒烟测试
   5.1 测试前提
       ——服务启动正常、健康检查通过、无 ERROR 级日志
   5.2 冒烟用例
       ——表格：序号、检查项、操作步骤、预期结果、实际结果、结论

6. 回滚方法
   6.1 回滚判定条件
       ——触发回滚的现象、决策人与决策时限
   6.2 回滚顺序
       ——表格：步骤、操作、执行脚本或命令、预期结果
   6.3 程序回滚
       ——版本包与配置的恢复方法
   6.4 数据库回滚
       ——回滚脚本或备份恢复方法，说明数据丢失与不可回滚范围
   6.5 回滚后验证
       ——版本核对、健康检查、冒烟复测

7. 其他注意事项
   ——停机与业务通知、脚本幂等性与重复执行、锁表与大事务、缓存与消息队列、定时任务、多节点滚动升级顺序、日志与监控、联系人

8. 文档修订记录
   ——表格：文档版本、日期、修订内容、修订人，位于正文最后
```

结构约束：

- 4.1 必须按实际顺序编排：获取脚本 → 前置校验 → 备份 → 执行数据库脚本 → 校验脚本结果 → 升级程序 → 服务可用性校验 → 冒烟测试 → 结果记录；本次无对应步骤时删除该行并顺延编号。
- 4.2 起每个步骤必须写明操作说明、执行命令、预期结果与失败处理；命令与 1.2 脚本清单、脚本头注释完全一致。
- 5 章只覆盖「系统能正常启动 + 基础功能可用」，不写本次升级功能的完整测试用例。
- 6 章必须给出可操作的回滚命令与顺序，不能只写「恢复备份」而不给恢复方式与验证方法。
- 第 8 章固定放在正文最后，每次修订追加一行，不覆盖历史记录。

## 脚本规范

### 类别与命名

每类脚本单独一个文件，本次没有该类变更就不生成。多个库或多个系统时加后缀区分，如 `upgrade-<库名>.sql`、`check-<系统名>.sh`。

| 类别 | 默认文件名 | 何时需要 |
|------|-----------|----------|
| 数据库变更 | `upgrade.sql` | 有表结构、索引、字典、初始化或数据变更时 |
| 前置校验 | `check.sql` / `check.sh` | 需要在执行前用脚本核对环境或数据时 |
| 结果校验 | `verify.sql` / `verify.sh` | 升级后需要用脚本核对执行结果时 |
| 执行编排 | `upgrade.sh` | 需要按顺序完成备份、执行 SQL、替换包、重启服务等多步操作时 |
| 回滚 | `rollback.sql` / `rollback.sh` | 数据库或程序变更需要脚本化回滚时 |

文件名、1.2 脚本清单、4.2 执行命令、脚本头注释四处必须一致。

### 通用要求

- 文件为 UTF-8 无 BOM；`.sh` 使用 LF 换行。
- 头部固定注释块七项：脚本名称、用途、适用版本、执行环境、执行方式、执行账号与所需权限、执行顺序（对应说明第 4 章的步骤号）。
- 执行命令同时写在说明 4.2 和脚本头注释中，两处必须一致，并保证可直接复制执行。
- 脚本可直接执行：不出现伪代码、TODO 或无法确定的内容；确需按环境填写的参数集中放在头部配置区并注明。
- 每个逻辑段、每条关键语句前有中文注释，说明做什么、为什么。
- 幂等：优先写成可重复执行；无法幂等时必须写明「只能执行一次」及判断是否已执行的查询。
- 失败即停：shell 使用 `set -euo pipefail`，关键步骤输出 `[OK]` / `[FAIL]` 并以非 0 退出；SQL 写明事务边界与失败后的处理。
- 不写密码明文：使用环境变量、交互输入或数据库客户端配置文件，并在注释中说明取值方式。

### 模板

以下模板中的 `<...>` 仅为说明，产出脚本不得保留占位符。

SQL：

```sql
-- =============================================================
-- 脚本名称: upgrade.sql
-- 用途: <本次数据库升级内容>
-- 适用版本: V<当前版本> -> V<目标版本>
-- 执行环境: <数据库类型与版本> / <字符集>
-- 执行方式: mysql -h<host> -P<port> -u<user> -p <库名> < upgrade.sql
-- 执行账号: 需具备 <DDL/DML> 权限
-- 执行顺序: 发版升级说明 4.2 第 <n> 步
-- 幂等说明: <可重复执行 / 只能执行一次及判断方法>
-- 回滚脚本: rollback.sql
-- =============================================================

-- 1. <变更说明>
<sql>

-- 2. <变更说明>
<sql>
```

Shell：

```bash
#!/usr/bin/env bash
# =============================================================
# 脚本名称: upgrade.sh
# 用途: <按顺序执行备份、SQL、替换发布包、重启服务等>
# 适用版本: V<当前版本> -> V<目标版本>
# 执行环境: <操作系统> / <部署方式>
# 执行方式: ./upgrade.sh   （或 bash upgrade.sh）
# 执行账号: <账号>，需具备 <权限>
# 执行顺序: 发版升级说明 4.2 第 <n> 步
# =============================================================
set -euo pipefail

# ---- 配置区：按环境修改 ----
APP_HOME="/opt/app"
DB_HOST="${DB_HOST:-127.0.0.1}"
DB_NAME="${DB_NAME:-<库名>}"
LOG_FILE="./upgrade-$(date +%Y%m%d%H%M%S).log"

# ---- 工具函数 ----
log() { echo "[$(date '+%F %T')] $*" | tee -a "$LOG_FILE"; }

# ---- 1. <步骤说明> ----
log "开始 <步骤>"
<command>
log "[OK] <步骤>"
```

### 文档与脚本一致性

- 1.2 脚本清单、4.2 执行命令、脚本头注释三处的文件名、命令与顺序必须一致。
- `upgrade.sql` 的语句与 2.1 变更清单中涉及数据库的条目逐条对应，数量与顺序一致。
- 回滚脚本覆盖 `upgrade.sql` 与 `upgrade.sh` 的每一项变更；无法回滚的变更必须在 6.4 与第 7 章写明影响与补偿方式。

## 写作规范

- 命令写完整可复制，包含必要参数；需要按环境调整的参数给出默认值或在配置区统一声明。
- 版本号、日期、路径、服务名全文统一，首次出现时给出定义。
- 结论性表述可判定，避免「尽量」「视情况」；确需条件判断时写明判定条件。
- 表格不嵌套，列表不嵌套；不使用 mermaid。
- 说明文档自成体系，不以「见某文档」代替具体步骤。
- 不写与升级无关的功能介绍、设计论证与完整测试用例。
- 文件为 UTF-8 编码，无 BOM。

## 输出

### 存放位置

默认根目录 `docs/05 rl/`，使用者另行指定时以指定为准；说明与脚本放在本次发版日期子文件夹下：

```
<根目录>/
└── <YYYY-MM-DD>/
    ├── 发版升级说明.md
    └── <按需生成的脚本>
```

`发版升级说明.md` 为固定文件名，每次发版一份。

### frontmatter

```yaml
---
title: <系统名称> 发版升级说明（V<目标版本>）
doc-type: RL
author: <作者>
version: V1.0
date: <YYYY-MM-DD>
confidentiality: 内部
cover: true
toc: true
---
```

取值规则：`title` 中的版本为目标发版版本；`version` 为本文档版本，首版 V1.0，每次修订递增（V1.1、V1.2…）并与第 8 章记录一致；`date` 取成文当天；`author` 取使用者指定的人。无法确定时留空字符串，并在交付对话中说明。

## 交付说明（仅在对话中输出，不写入文档）

交付时在对话中说明：

- **本次模式**：新建还是修订；修订时列出改动了哪些章节与脚本。
- **目录与文件清单**：子文件夹路径、说明文档、各脚本及其执行顺序。
- **待确认事项**：未确认的内容不写入文档，在对话中逐条列出，写明问题、依据、需确认人与影响范围。
- **风险提示**：是否停机、是否存在锁表或大事务、是否有不可回滚项、数据兼容性风险。
- **资料缺口**：使用者未提供且影响升级可执行性的信息（如发布包路径、服务启停方式、数据库连接信息、回滚包），说明影响哪一章节或哪个脚本。

## 自检清单

**结构完整性**

- frontmatter 字段齐全且取值符合规则。
- 1~8 章齐全；4.1 步骤覆盖获取脚本、前置校验、备份、执行、校验、升级程序、可用性校验、冒烟与记录。
- 每个脚本在 1.2 脚本清单中登记，清单中每个脚本都真实存在。
- 修订模式下未新建多余文件夹；确需重新创建时子文件夹后缀未与已有文件夹重复。

**内容准确性**

- 升级内容、表名、字段名、命令、路径均能追溯到变更材料、现有系统或使用者确认，无编造。
- 脚本清单、执行步骤、脚本头注释三处的文件名、命令与顺序一致。
- 数据库脚本覆盖变更清单中的全部数据库变更；回滚脚本覆盖全部可回滚项，不可回滚项已写明。
- 冒烟测试只覆盖启动与基础功能，预期结果可判定。
- 正文无「待确认」「TODO」等残留，未确认事项只在交付对话中列出。

**格式与可执行性**

- 脚本头注释七项齐全，执行命令可直接复制执行。
- SQL 标注 `sql`，shell 标注 `bash`；shell 有 shebang、`set -euo pipefail`、失败退出。
- 无密码明文；无伪代码与占位符残留。
- 表格与列表不嵌套；文件为 UTF-8 无 BOM，`.sh` 为 LF 换行。
