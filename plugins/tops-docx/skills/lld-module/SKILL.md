# 模块设计说明书 (lld-module)

## 用途

撰写详细设计阶段的**模块设计说明书**，把业务功能细化到可实现、可编码的粒度：模块组成、关键类与函数、内部处理流程、状态与数据、异常处理、并发与幂等、关键流程、配置与日志、单元测试要点。

**本技能可以脱离 HLD 独立使用**：有 HLD 时从 HLD 的模块划分与职责推导；没有 HLD 时，按需求中的业务能力与职责边界自行划分模块，或沿用现有代码的模块结构。

本技能只负责模块内部设计内容，不写表结构、接口报文、部署与运维。本技能只负责「写成 markdown」；需要 Word 文档时，由使用者再调用 `md2docx` 技能按 docx 模板转换。

## 触发条件

- 使用者要求「写模块设计」「写模块详细设计」「写详细设计（模块部分）」「写实现设计」时使用。
- 使用者提供需求、HLD（如有）、现有代码或系统资料，并要求据此细化某个模块或全部模块时使用。
- 使用者说 `/lld-module` 时使用。
- 只需要表结构或接口字段时，不使用本技能。

## 输入来源与证据优先级

按以下优先级取证，高优先级来源覆盖低优先级来源：

| 优先级 | 来源 | 用于确认 |
|--------|------|----------|
| 1 | 使用者当前在对话中提供的需求、业务功能、模块划分与职责 | 覆盖范围、职责边界、依赖关系、交互方式 |
| 2 | 使用者指定路径的 HLD（如有）、PRD、现有系统设计文档 | 模块清单、模块交互、数据约束、非功能要求 |
| 3 | 现有代码、类图、配置样例、运行日志、公共组件说明 | 实现现状、可复用组件、实际处理分支 |
| 4 | 使用者口述的补充说明与团队实现规范 | 分层约定、编码规范、并发与事务策略 |

**检索与降级规则**：

- **HLD 不是必需输入**。没有 HLD 时，直接按需求、现有代码或使用者口述取证，不要求使用者先补 HLD。
- 没有 HLD 且材料中也没有明确模块划分时，按业务能力与职责边界提出模块划分建议并直接成文，在交付对话中说明划分依据。
- 优先使用使用者当前提供的形式；对话中已粘贴的内容不再重复读取文件。
- **不要求任何输入文件存在于固定路径**——本技能必须能脱离仓库中的文档独立成文。
- 文件可能因加密、损坏或格式不兼容而无法读取；读不到即降级取证，**不要根据文件名或常识臆测其内容**。
- 优先级 1~3 都拿不到足够的业务与实现信息时，先向使用者索取必要输入；仅个别细节无法确认时，不中断成文。
- 现有代码中存在但材料未覆盖的逻辑，不擅自写入正文，在交付对话中列出。
- 现有代码与需求或设计划分冲突时，以使用者确认的设计为准，代码只作实现参考。

## 工作流

1. 确认项目/特性名称、使用者指定的输出目录、覆盖的模块范围，以及采用单模块一份还是多模块合订。
2. 从可用材料中提炼模块清单（`M-` 编号）与职责边界；材料不足以划分模块时，按业务能力与职责边界提出划分建议，不中断成文。
3. 梳理模块依赖与对外交互，登记使用的数据对象、外部系统与公共组件。
4. 按「章节骨架」逐模块细化：职责与组成、关键类与函数、处理流程、状态与数据、异常处理、并发与幂等。
5. 展开关键流程、配置与日志、单元测试要点。
6. 按「自检清单」逐项核对。
7. 交付时在对话中列出待确认项、设计缺口与建议补充材料，不写入文档。
8. 告知使用者将要写入的文件路径；目标文件已存在时先询问覆盖还是改名，确认后再写入。

## 冲突处理

- 使用者当前答复与既有文档不一致：以使用者当前答复为准，差异在交付对话中说明。
- 需求文档、HLD（如有）与现有代码不一致：以使用者确认的设计为准，代码只作实现参考；差异及处理方式在交付对话中说明。
- 模块职责在不同材料中冲突：以带模块编号或职责定义的条款为准；仍无法判断时按现有材料取最合理方案成文，并在交付对话中列出。
- 实现细节无法确认（并发策略、事务边界、幂等规则、超时取值、配置默认值、状态流转）时按现有材料取最合理方案成文，并在交付对话中列出，写明影响的模块或流程。

## 章节骨架

文档按下述多级章节组织，`<...>` 处按实际项目替换，`——` 后为该节应包含的内容。固定章节不得删减；项目无对应内容时删除该节并顺延编号，不留空节。

```
1. 文档概述
   1.1 编写目的
   1.2 设计范围
       ——本文档覆盖的模块、模块数量，以及明确不包含的部分
   1.3 读者对象
       ——表格：读者角色、关注内容
   1.4 术语与缩略语
       ——表格：术语/缩略语、全称或含义、说明
   1.5 编号与命名约定
       ——表格：编号前缀、对象、使用范围
       ——模块、类、数据结构、配置项的命名规则与示例

2. 模块总体说明
   2.1 模块清单
       ——表格：模块编号、模块名称、职责概要、划分依据、本文档是否覆盖
   2.2 模块依赖关系
       ——表格：模块编号、依赖对象、依赖方式（调用接口/读写数据/消息/公共组件）、依赖说明
   2.3 技术栈与实现约定
       ——语言与版本、框架、分层方式、公共组件、编码规范要点

3. 模块详细设计
   3.1 <模块一>
       3.1.1 职责与组成
           ——本模块负责什么、不负责什么，由哪些类或组件构成
       3.1.2 关键类与函数
           ——表格：名称、类型、职责、输入、输出、异常
       3.1.3 内部处理流程
           ——按步骤编号，标明分支条件与状态变化
       3.1.4 状态与数据
           ——涉及的状态及取值；使用的数据对象与表（写名称，字段只列本模块使用的关键字段）；本模块私有数据结构完整定义
       3.1.5 异常处理
           ——本模块可能出现的异常、检测条件、处理方式、对外表现
       3.1.6 并发与幂等
           ——并发点、锁或幂等策略、重入与重复提交的处理方式；无并发访问时删除本节
   3.2 <模块二>
       ——结构同 3.1
   3.N <模块 N>
       ——结构同 3.1

4. 关键流程设计
   4.1 <流程一>
       ——触发条件、参与模块、详细步骤（按顺序编号）、状态变化、异常分支
   4.2 <流程二>
       ——结构同 4.1
   4.N 跨模块协作流程
       ——按接口或消息串联的完整调用链，标明同步或异步、超时与失败处理
   4.M 并发与重入处理
       ——跨模块并发点、锁顺序、幂等键、重试与补偿策略

5. 配置与日志
   5.1 配置项
       ——表格：配置项名称、含义、默认值、取值范围、生效方式、所属模块
   5.2 日志设计
       ——表格：日志级别、记录点、记录内容、是否含敏感信息、所属模块

6. 单元测试要点
   6.1 关键分支覆盖
       ——需要覆盖的主流程、分支与判定条件
   6.2 边界条件
       ——需要验证的边界值与极端输入
   6.3 测试替身与桩
       ——需要替换的外部依赖及替身说明

7. 文档修订记录
   ——表格：版本、日期、修订内容、修订人，位于正文最后
```

结构约束：

- 全文编号连续，层级不超过四级。模块使用 `M-01`（项目已有模块编号时沿用，无既有编号时在本册定义），模块内部私有数据结构使用 `DM-01` 或 `DM-<模块号>-01`（同一文档内风格统一）；同一对象在全文中只使用一个编号。
- 1.5 节只写本文档使用的编号前缀、命名规则与示例，不引入本文档之外的设计内容。
- 2 章先给模块清单、依赖与技术栈，不写单个模块的内部细节；没有既有模块划分时，2.1 必须写明划分依据。
- 3 章按模块逐个展开。`3.x.1` 至 `3.x.5` 五节必须齐全，不得缺节或合并；`3.x.6` 有并发访问时保留，无并发访问时删除本节。
- `3.x.4` 中，跨模块共用的数据对象与表只写名称和本模块使用的关键字段，不重复完整字段定义；本模块私有结构用 `DM-` 编号定义，写全字段。
- 4 章按关键流程组织，每条流程写明触发条件、参与模块、步骤与异常分支；跨模块协作与并发重入可单独成节。
- 单模块文档只保留该模块的 3.1，后续模块小节删除并顺延编号；多模块合订按 3.1、3.2 依次展开。
- 5 章只写配置项定义与日志记录点，不写具体环境的配置值、日志平台部署与运维操作。
- 6 章只写需要覆盖的分支、边界与测试替身，不写测试执行记录与缺陷记录。
- 7 章固定放在正文最后，不并入概述；每次修订追加一行，不覆盖历史记录。

## 写作规范

**设计表述**

- 每项设计写成可判定的陈述，说明输入、处理、输出与异常结果；一个步骤只做一件事。
- 模块职责用「负责……」「不负责……」界定边界；同一职责不得分配给多个模块。
- 关键类与函数写全：名称、类型、职责、输入、输出、异常；不展开到逐行实现。
- 状态流转写成可判定的规则：当前状态、触发条件、目标状态、执行动作、异常处理。
- 模块、类、函数、数据结构、配置项的名称全文统一，首次出现时给出定义。

**代码片段**

- 代码片段放在围栏代码块中，并标注语言。
- 代码只用于表达关键算法、结构定义或调用示例，不粘贴完整实现。
- 同一数据结构只在一处给出定义，其他位置引用其名称与编号。

**文档自洽**

- 本文档自成体系：模块职责、流程、状态、异常与私有数据结构均在本册内完整定义，不要求读者查阅其他设计文档或需求文档才能理解正文。
- 不写「见某文档第 X 节」「详见数据库设计/接口设计」一类跨文档引用；确需提及项目中的其他对象（表、接口、外部系统）时，只写名称，不展开引用。

**内容边界**

- 不写架构选型论证与需求复述。
- 不写表结构逐字段定义、建表 SQL、接口报文字段与错误码全表。
- 不写部署架构、网关配置、日志平台与运维操作。
- 不写具体测试用例步骤、测试数据与缺陷记录。

**格式**

- 时序图、状态图用编号步骤、表格或缩进文本表达，不使用 mermaid。
- 表格不嵌套，列表不嵌套。
- 文件为 UTF-8 编码，无 BOM。

## 输出

### 存放位置

单模块一份时：

```
docs/<项目或特性>/LLD-<模块名称>模块设计.md
```

多模块合订时：

```
docs/<项目或特性>/LLD-<项目或特性名称>模块设计.md
```

使用者指定目录时以使用者指定为准；多个模块各一份时，文件名中的模块名称必须能唯一区分，同项目命名风格保持一致。

### frontmatter

文件顶部必须包含以下字段（字段名固定，供 `md2docx` 识别封面信息）：

```yaml
---
title: <项目或特性名称> <模块名称>模块设计说明书
doc-type: LLD
doc-part: MODULE
modules: M-01, M-02
version: V1.0
author: <作者>
date: <YYYY-MM-DD>
confidentiality: 内部
cover: true
toc: true
---
```

取值规则：`doc-part` 固定为 `MODULE`；`modules` 列出本文档覆盖的模块编号，单模块填一个（无既有编号时用本册定义的编号）；`author` 默认取使用者指定的人或需求文档的修订人；`date` 取成文当天；首版 `version` 为 V1.0。确实无法确定时留空字符串，并在交付对话中说明。

### 图片

- 类图、流程图、状态图放在 md 文件同级的 `images/` 目录，命名 `lld-module-<章节号>-<序号>.png`，引用写法 `![图题](images/xxx.png)`。
- 没有可用的图片素材时，不写入指向不存在文件的图片引用，也不留空占位，改用编号步骤或表格表达。

## 交付说明（仅在对话中输出，不写入文档）

交付文档时在对话中说明三项：

- **待确认清单**：列出成文过程中未能确定、按假设写入的事项，每条写明当前采用的假设、依据、影响范围与需确认人。
- **设计缺口**：列出材料未覆盖但实现必须确定的问题（如并发策略、事务边界、幂等规则、超时取值、配置默认值、状态流转），说明缺失影响哪一章节。
- **建议补充材料**：按章节列出建议补充的现有代码、类图、配置样例、运行日志或公共组件说明；没有可用的材料时必须输出。

## 自检清单

**结构完整性**

- frontmatter 字段齐全且取值符合规则，`modules` 与实际覆盖范围一致。
- 1~7 章齐全；3 章每个模块的 `3.x.1`~`3.x.5` 齐全。
- 已识别的每个模块在 2.1 有登记、在 3 章有展开（本文档范围之外的模块须在 2.1 标注「未覆盖」）。

**内容准确性**

- 每个关键类与函数写明输入、输出与异常；每条流程的异常分支都有处理方式。
- 状态与数据写明状态取值、使用的数据对象与关键字段；模块私有结构用 `DM-` 编号定义且字段完整。
- 模块依赖的方向与依赖对象明确，无循环依赖或已注明处理方式。
- 配置项均写明默认值与生效方式；日志记录点标明级别与敏感信息处理。
- 无架构论证、表结构、接口报文、部署与运维细节。

**格式规范**

- 表格与列表均为单层，无嵌套；不使用 mermaid 或流程图代码块。
- 编号连续，无重复；不出现跨文档引用。
- 代码片段均在围栏代码块中并标注语言。
- 正文无「待确认」「TODO」等字样残留。
- 文件为 UTF-8 编码且无 BOM。
