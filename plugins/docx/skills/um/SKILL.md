# 用户操作手册 (um)

## 用途

撰写面向最终用户的**用户操作手册**，说明功能用途、界面位置与操作步骤，输出为 UTF-8 编码的 markdown 文件。

本技能只负责「写成 markdown」。需要 Word 文档时，由使用者再调用 `md2docx` 技能按 docx 模板转换。

## 触发条件

- 使用者要求「写用户手册」「写操作手册」「写使用说明」时使用。
- 使用者提供 PRD 并要求面向用户产出操作说明时使用。
- 使用者说 `/um` 时使用。

## 输入来源

内容**由 PRD 与代码共同推导**：

1. **PRD**：确定手册覆盖的功能范围与业务规则。获取方式为使用者粘贴、指定路径的本地文件或口述要点；都拿不到时先索取。
2. **代码库**：确认界面元素名称、菜单层级、按钮文案、字段含义、提示信息与操作路径。

**关键约束**：

- 先读代码（界面资源、文案、菜单定义、错误提示等）确认实际存在的功能与操作路径，**不得虚构不存在的菜单、按钮或步骤**
- 代码中找不到对应实现的功能，向使用者确认后再决定是否写入手册
- 代码中的文案与 PRD 表述不一致时，以实际界面文案为准，并向使用者指出差异

## 工作流

1. 确认项目/特性名称与手册覆盖范围。
2. 取得 PRD 内容，列出手册要覆盖的功能清单。
3. 在代码库中定位这些功能的界面与操作路径（界面定义、文案、菜单、提示信息、错误码）。
4. 按「章节骨架」逐章成文，操作步骤以用户视角描述：进哪里、点什么、填什么、看到什么。
5. 自检：每个操作步骤在代码中都找得到依据、步骤可直接照做、术语与界面文案一致、无跨文档引用。

## 输出

### frontmatter

文件顶部必须包含以下字段（字段名固定，供 `md2docx` 识别封面信息）：

```yaml
---
title: <项目或特性名称> 用户操作手册
doc-type: UM
version: V1.0
author: <作者>
date: <YYYY-MM-DD>
confidentiality: 限制
cover: true
toc: true
---
```

字段值未知时向使用者确认；确实无法确认时留空字符串，并在成文后列出待补充字段。

## 章节骨架

### 1. 概述

- **写**：项目背景、编写目的、适用范围、术语与缩写
- **不写**：设计原理

### 2. 运行环境与安装

- **写**：软硬件环境要求、安装/升级步骤、首次使用前的准备
- **不写**：部署架构、运维操作

### 3. 软件功能说明

- **写**：主界面区域划分、菜单结构、常用控件与图标含义
- **不写**：具体操作步骤

### 4. 应用场景操作流程

- **写**：按应用场景编写操作流程
- **不写**：功能的设计原因、异常处理的技术细节
- 每个应用场景单独一个章节
- 应用场景下应包括：适用场景、前提条件、操作步骤、注意事项

### 5. 常见问题与故障处理

- **写**：用户可自行处理的常见问题、现象、原因、处理步骤
- **不写**：需要研发介入的内部排查过程


## 注意事项

- **每个操作步骤都要有代码依据**，找不到实现的功能不写；确实要写时先向使用者确认
- 界面文案以代码中的实际文案为准，不要自行改写按钮、菜单、提示信息的名称
- **不得引用其他文档**：不出现「见 PRD」「详见详细设计」一类跨文档引用，手册必须能单独交付给最终用户
- 截图以本地图片引用（`![图题](images/xxx.png)`），图片路径相对 md 文件；图片文件不存在时在文中标注待补
- 表格**不要嵌套**，列表**不要嵌套**——`md2docx` 的解析器只支持单层结构
- 操作路径用「菜单 → 子菜单 → 按钮」这类纯文本写法，不要使用 mermaid
- 文件必须为 UTF-8 编码
- 本技能不生成 docx；使用者需要 Word 版本时提示其调用 `md2docx` 技能
